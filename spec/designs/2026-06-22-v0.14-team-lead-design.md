# v0.14 设计源稿 · Team Lead（长期团队 + 多队员并行协作）

> **状态：脑暴源稿（DRAFT）。** 不是四件套 spec，是喂给日后 v0.14 `spec/{spec,plan,task,checklist}.md` 的上游设计。
> **排期决策（2026-06-22，用户拍定）：先收尾 v0.13 普通子 Agent 路径（T142–T147），再正式做 v0.14。** 故本稿先冻结方向与三大决策，待 v0.13 落地后再细化为四件套并校准接口。

## 一句话目标

把主 Agent 升级为 **Team Lead**：能创建**长期存在**的团队、派生多个队员**并行**干活；队员之间通过**共享任务列表 + 邮箱**直接协作（不必所有信息经 Lead 中转）；Lead 可开启 **coordinator 模式**，专注派人/决策，把代码修改交给队员。

## 组件模型

### A. 团队对象（Team / 小组，长期存在）
- 字段：`name`（唯一）、`lead`（负责人标识）、`members`（花名册）、`persist_dir`（持久化位置 = `~/.config/wentian/teams/<name>/`）。
- 成员（Member）字段：`role`（角色名，索引到 v0.13 `AgentRegistry`）、`cwd`（工作目录 = 该成员的 git worktree）、`backend`（运行后端）、`needs_approval`（是否要 Lead 审批才动手）、`status`（idle/running/...）、`branch`（独立分支名）。

### B. 成员运行后端（按环境优先级自动选，不静默降级）
1. **独立进程（强隔离）**：在独立终端窗格里跑**完整 wentian 实例**。
   - 窗格来源优先级（探测可用性）：tmux split-window ▸ Warp/iTerm 原生分屏 ▸（都不可用则降级）。
   - 长驻进程：跑完一轮自然停下后**驻留等邮箱**（idle），被 Lead「唤醒窗格」后继续；不重头 spawn。
2. **同进程协程（轻量）**：复用 v0.13 `run_subagent`（worker 线程 + 隔离 AgentLoop）。无强隔离但零额外进程。
- **降级铁律**：想要独立进程但窗格后端都不可用 → 落到同进程协程时**必须显式告知用户**，绝不静默。

### C. 协作工具（仅队员/Lead 可见，主入口 + 普通子 Agent 看不到）
- **共享任务 CRUD**（带依赖字段 `depends_on`）：增 / 删 / 查 / 改 + 列。落在团队共享清单（持久化）。
- **点对点发消息**：P2P + 广播 + 几种结构化协议消息。
- **可见性门**：工具是否暴露取决于「当前是不是某团队的成员/Lead」——主 REPL 普通态、v0.13 普通子 Agent **都拿不到**这组工具（复用 v0.13 `resolve_allowed_tools` 的过滤思路扩展一个「团队上下文」维度）。
- **审批流**：`needs_approval` 的队员先把计划经协议消息发给 Lead；Lead 用一种**特定结构的回复**（APPROVE / REJECT + 理由）批准或驳回，队员收到 APPROVE 才开干。

### D. 点对点消息（两段式：名称注册表 + 邮箱文件）
- **名称注册表**：member name → 邮箱路径 / 后端 / 窗格句柄 的映射（团队元数据里）。
- **邮箱文件**：每成员一份，落 `~/.config/wentian/teams/<name>/<member>/mailbox.*`。
- **独立进程后端额外**：投递后**唤醒目标窗格**（tmux send-keys / 终端原生唤醒），让驻留的 idle 实例醒来读信。
- **结构化协议消息类型**（初版枚举，待 spec 细化）：`TASK_ASSIGN`、`PLAN_REVIEW`（队员→Lead 求审）、`APPROVE` / `REJECT`（Lead→队员）、`IDLE`（队员→Lead 报空闲）、`DONE`（队员→Lead 报完成）、`QUESTION` / `ANSWER`（P2P）、`BROADCAST`（群发）。

### E. 发起方 = Lead（编排）
1. 把用户目标**拆成带依赖的任务**写进共享清单。
2. **派生成员**（各自 worktree + 分支 + 后端）。
3. 全部完成后**用 git 合并各分支**：能解决的冲突解决、搞不定**回滚 + 上报**。
4. coordinator 模式下 Lead 自己不改文件，靠 shell 跑 git 合并。

### F. 成员 idle + 磁盘恢复（不重头 spawn）
- 队员干完自然停下 → 标记 `idle` + 通知 Lead。
- Lead 之后发消息 → 从磁盘**恢复该成员上下文**继续指派（复用 v0.9 会话 JSONL 持久化/恢复机制）。

### G. coordinator 开关（双锁，两把都开才生效）
- **锁一（能力）**：配置里先开 capability 开关（暂定 `teams.coordinator_capable: true`）。
- **锁二（启用）**：用户用环境变量主动启用（暂定 `WENTIAN_COORDINATOR=1`）。
- 生效后：**剥夺发起方的写文件工具**（`write_file`/`edit` 类），**保留读类工具 + shell**（合并要靠 shell 跑 git）；只留：**派人 / 终止 / 发消息 / 合并代码** 这几件事。

## 持久化与消息格式

- 团队配置持久化到 `~/.config/wentian/teams/<name>/`：内含各成员的**邮箱**与**元数据**。
- **一条消息**字段：`sender`、`body`、`timestamp`、`read`（已读标记）、`summary`。
  - 落盘时**自动补 timestamp**、`read` **默认未读**。
- **邮箱文件并发安全**：用**锁文件**；拿不到锁就**重试**；锁**太旧视为过期**（可被抢占）。

## 本步不做（明确 YAGNI）

- 跨机器分布式团队。
- 成员间实时流式通信（消息走邮箱轮询/唤醒，不做 streaming）。
- 更复杂的任务依赖约束（只做单一 `depends_on` 字段，不做 DAG 调度器/优先级/资源约束）。
