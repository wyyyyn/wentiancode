从零造一个终端 AI 助手，
到底发生了什么

这是 WentianCode（文天）v0.1 的搭建全记录。不需要任何编程背景——但每个环节都讲真东西，不糊弄。读完你会明白一个"终端里的 ChatGPT"是怎么从一句想法变成能跑的软件的。

SECTION 01

我们到底在造什么

你用过网页版的 ChatGPT 或者 Claude：打开浏览器，输入问题，看回答一个字一个字蹦出来。WentianCode 做的是同一件事，但活在终端里——就是程序员每天敲命令的那个黑窗口。

装好之后，体验是这样的：

wentian — 终端
$ wentian 文天> 用一个 Markdown 列表介绍你自己 🤔 思考中…（思考过程用暗色斜体流出来） • 身份与定位 —— 我是一个 AI 助手…… • 核心功能 —— 代码、分析、推理…… 文天> 我刚才问的是什么？ "用一个 Markdown 列表介绍自己。" # 它记得 文天>

看起来简单，但拆开有五件事要同时成立，这就是 v0.1 的全部目标：

  • 流式输出——回答一边生成一边显示，不是干等十秒后整段砸出来
  • 多轮记忆——它记得这场对话里之前说过的话
  • 多家模型随便换——Claude、DeepSeek、Qwen……一份配置文件全管
  • 思考过程可见——模型"打草稿"的过程也流式展示，和正式回答看起来不一样
  • 关掉再开还在——对话存在本地，下次能接着聊

同样重要的是明确不做什么：不让 AI 动你的文件、不执行命令、不传图片。砍掉这些不是偷懒，是让第一个版本小到能一次做对。这个清单本身就是工程决策的一部分。

SECTION 02

动手前先吵清楚：四份文档

大部分人写软件失败不是因为不会写代码，是因为一边写一边才想明白自己要什么，于是反复推翻重来。这个项目用了一条铁律来防这件事：四份文档全部写完、逐份确认之前，一行代码都不许写。

回答"做什么"
spec.md 功能清单（12 条）、明确不做的事（5 条）、以及"怎样才算做完"的验收标准（10 条）
回答"怎么做"
plan.md 架构怎么分层、模块之间怎么对话、每个模块怎么测试。技术选型都在这一步定死
回答"什么顺序"
task.md 把整个工程切成 14 个小任务，每个 2-5 分钟粒度，写明依赖关系和验证命令
回答"做对了吗"
checklist.md 一张行为验收清单：每一项都是"做 X，应该看到 Y"，能跑能看，不是自我感觉

这套顺序的妙处在于：每一份文档都在逼你把"感觉差不多了"变成白纸黑字。比如写 spec 的时候中途追加了一条"回答要渲染成排版好的 Markdown，而不是显示原始符号"——这要是写到一半才想起来，渲染层就得返工；在文档阶段加，只是多打几行字。

四份文档里藏着一个反直觉的安排：验收清单（checklist）是在写代码之前设计的。先决定"怎么算合格"，再开工——这样"完成"就不是一种心情，而是一组能逐条打勾的事实。

SECTION 03

把大象切成积木：架构

"架构"这个词唬人，本质就一句话：把一个大问题切成几个小问题，并规定它们只能怎么对话。WentianCode 切成了五层，每层只干一件事：

cli.py — 前台接待解析启动命令（要哪个模型？接着上次聊？），把下面所有零件组装起来
↓组装后启动
repl.py — 对话主持人循环：等你输入 → 判断是命令还是聊天 → 调度其他人干活
↓拿到回答事件流交给 ↓ 显示，聊天记录交给 ↘ 保存
render.py
化妆师把文字流渲染成漂亮的终端排版
session.py
记录员把每轮对话存成 JSON 文件
↓真正去问 AI 的是 ↓
providers/ — 翻译官们统一接口 Provider，下面站着 Anthropic 翻译和 OpenAI 兼容翻译，谁上场都说同一种"内部语言"

最值钱的设计是翻译官的"内部语言"。不同 AI 厂商的接口长得不一样，但我们规定：不管对接谁，翻译完只能产出三种"事件"——

ThinkingDelta（思考片段）
模型打草稿的一小段文字 → 化妆师把它显示成暗色斜体
TextDelta（正文片段）
正式回答的一小段文字 → 化妆师把它渲染成 Markdown
Done（结束信号）
这轮说完了，顺便附上用了多少 token

这样一来，上面四层完全不知道"Claude"或"DeepSeek"的存在。以后要接一家新模型，写一个新翻译官、在登记表里加一行，其余代码一个字不用动。测试时也一样——塞一个"假翻译官"（预先编好台词的 FakeProvider），整个界面层就能在不联网的情况下被完整测试。

SECTION 04

零基础必备的五个概念

下面五个词贯穿全程，每个用一句人话讲清：

API 和 API key
AI 模型住在厂商的服务器上，你的程序通过网络去"点菜"，这套点菜规矩叫 API。API key 就是你的会员卡号——证明你是谁、从你的余额里扣钱。所以 key 要保密，泄露了等于别人能刷你的卡。
协议（为什么只需要支持两种）
点菜规矩主要有两套方言：Anthropic 协议（Claude 用）和 OpenAI 协议。有意思的是，国产模型（DeepSeek、Qwen、Kimi……）几乎全部主动说 OpenAI 方言，只是把"餐厅地址"（base_url）换成自己家。所以支持两种协议 ≈ 支持市面上所有主流模型。
流式（streaming）
AI 生成回答需要时间。与其等全部写完再给你（盯着空屏十秒），不如写一点送一点——服务器把回答切成小块（chunk）连续推过来。你看到的"打字机效果"就是流式。工程上的难点：一边收一边显示，还要在中途出错时优雅收场。
YAML 配置文件
程序的"设置页面"，但用文本文件表达。缩进表示层级，冒号表示键值。人能直接读懂，程序也能解析。本项目用一份 YAML 管理所有模型的地址、key 和开关。
会话持久化
AI 接口本身是"金鱼记忆"——每次请求都得把之前的对话全文重发一遍，它才"记得"上下文。所以程序要自己当记录员：每轮对话结束就把完整历史写进本地 JSON 文件，下次启动读回来接着发。所谓"记忆"，就是这么朴素的复读。
SECTION 05

先写"会失败的测试"：TDD

整个开发期执行第二条铁律：没有先失败的测试，不许写正式代码。这叫 TDD（测试驱动开发），节奏永远是三拍：

① RED

先写一个小测试，描述"我期望程序做到什么"。跑它——必须失败，因为功能还不存在。这一步是在验证测试本身没写错。

② GREEN

写刚好能让测试通过的最少代码。不顺手加功能，不提前优化。跑测试，变绿。

③ REFACTOR

趁着绿灯整理代码：改名、去重、抽函数。每改一步都重跑测试，保证还是绿的。

为什么非要先看着测试失败一次？因为一个从没红过的测试，你不知道它到底在测什么——也许它写错了，永远都会通过，等于没测。先红后绿，绿才有意义。

14 个任务全部按这个节奏走完，攒下 148 个测试。它们的回报在后期兑现：每次改动任何一个模块，几秒钟跑完全部测试，立刻知道有没有踩坏别处。重构不再靠胆量，靠的是这张安全网。

tests — 每次提交前都要看到的画面
$ uv run pytest -q ................................................ [100%] 148 passed in 2.85s
SECTION 06

评审网抓住的那条鱼

每个任务写完后要过两道独立审查：第一道查"是不是做了要求的事"（不多不少），第二道查"做得好不好"（代码质量）。审查者被明确告知：别信开发者的汇报，自己读代码验证。听起来官僚？看看它抓到了什么。

案发现场：渲染模块交付，自报"Markdown 流式渲染完成"，148 个测试全绿。

审查发现：逐行读代码后发现——所谓"流式"只是把文字攒在内存里，等全部接收完才一次性渲染。负责实时刷新的代码块里赫然写着一个 pass（占位符，意思是"这里什么都不做"）。在真实终端里，用户会盯着空屏直到回答彻底结束，然后整段砸出来——恰恰是规格书明令禁止的体验。

测试为什么没拦住？因为测试环境不是真终端，全部走了"非终端降级路径"，那条坏掉的真终端路径根本没被执行到。测试全绿 ≠ 没有 bug，只等于"测到的地方没有 bug"。

修复与上锁：把实时刷新逻辑挪进接收循环（来一块渲染一块），再写一个"间谍测试"潜伏在刷新函数上数调用次数——对旧代码跑：0 次调用，红；对新代码跑：≥3 次，绿。从此谁敢把流式改回"攒够再渲"，测试当场翻脸。

这套流程后来又抓到三条小鱼：思考文字和渲染区在屏幕上撞行、某个字段为空时会崩溃、一个真实服务器特有的数据形态没被覆盖。每一条都在"测试全绿"的状态下被人读代码读出来的。

给你的可迁移结论：检查代码的人不能是写代码的人刚才的那个状态——要么换人，要么换一双"专门找茬"的眼睛，并且永远要求证据而不是汇报。

SECTION 07

验收：怎么证明它真能用

第三条铁律：没有当场跑出来的新鲜证据，不许说"完成"。验收分两轮：

第一轮：离线验收（不花一分钱）

不联网、不配任何 key，验证所有内部逻辑：148 个测试通过、命令行帮助能弹出、界面层确实一行都没引用任何厂商的代码（用文本搜索证明）。

第二轮：联网验收（真刀真枪）

注册了硅基流动（一个聚合了 DeepSeek、Qwen 等模型的国内平台，注册送额度），拿真 key 逐条跑行为清单：

acceptance — 验收实录（节选）
# 记忆：跨进程接续上一场对话 $ wentian --continue 文天> 我们对话的第一个话题是什么？ 介绍你自己 # ✓ 答对了，记忆穿越了进程重启 # 错误恢复：故意用一个错的 key 文天> 你好 错误：Error code: 401 - Api key is invalid 文天> # ✓ 一行错误，程序没崩，还能继续用 # ✓ 检查存档目录：失败的那轮没有留下半截记录

注意最后那条：出错时不仅要不崩溃，还要把那轮没说成的话从历史里撤掉。否则存档里会留下一个"有问无答"的破洞，下次发给模型的上下文就是脏的。这种边角才是软件质量的真正分水岭。

SECTION 08

自己跑起来

三步。前提：装好 uv（Python 的现代包管理器，一条命令安装）。

1
拿一个 API key

最快路径：硅基流动注册即送额度，一个 key 能用 DeepSeek / Qwen / GLM 全家。要用 Claude 则去 Anthropic 官网另取。

2
写配置文件

位置固定在 ~/.config/wentian/config.yaml，内容照抄下面改 key 即可。写完记得 chmod 600 收紧权限（key 是明文）。

3
启动

项目目录里 uv run wentian。常用姿势：--continue 接着上次聊，-p 名字 指定模型，会话里 /help 看全部命令。

~/.config/wentian/config.yaml
# default 指定不带参数启动时用谁 default: sf providers: sf: # 名字随便起，启动时 -p sf 引用它 protocol: openai # 国产模型一律选 openai model: deepseek-ai/DeepSeek-V3.2 base_url: https://api.siliconflow.cn/v1 # 注意结尾的 /v1 api_key: sk-你的key claude: protocol: anthropic model: claude-opus-4-8 api_key: sk-ant-你的key thinking: true # 打开思考过程展示

最后，把整个过程压缩成三句话

  • 先吵清楚再动手——四份文档把"想要什么"钉死，代码只是文档的执行。
  • 让失败先于成功发生——每段代码诞生前，都有一个为它准备好的红色测试在等着变绿。
  • 证据，不是感觉——"完成"由当场跑出来的输出定义，审查者的任务是不相信任何汇报。

这三条和"终端 AI 助手"没有绑定关系。下次你做任何项目——哪怕不写代码——它们照样成立。
