SECTION 01

从"动嘴"到"动手"

前两版的文天是个纯聊天的助手：你问它"快速排序怎么写"，它给你一段代码——但它看不到你电脑里真实的文件，也碰不了它们。你得自己复制粘贴。它像一个隔着玻璃的专家：能说，不能动。

v0.3 干的事，就是在玻璃上开一扇带锁的门。从这一版起，模型可以在回复里说"我需要读一下 pyproject.toml"，程序真的去读，把内容塞回给它，它再据此回答。一来一回，助手第一次真正"看见"并"动到"了你的项目。

wentian — 一次真实的工具往返
$ wentian 文天> 读一下 pyproject.toml，现在是第几版？ ⏺ read_file(path='pyproject.toml') # ← 模型请求调工具 ⎿ 成功 · [project] # ← 程序执行，结果回灌 当前版本是 0.3.0。 # ← 模型据此作答 文天> 把 README 顶部标题改成「文天 · WentianCode」 ⏺ edit_file(path='README.md', old_string='# WentianCode', …) Run tool 'edit_file' with: …? 执行该操作？[y/N] y # ← 改文件，先问你点头 ⎿ 成功 · Edited README.md: replaced 1 occurrence. 已改好。

看着简单，背后要同时立住一串设计。这一版的全部目标，是让下面六件事都能干，而且干得安全、不崩：

  • 读文件 / 写文件 / 改文件——改文件用"原文精确替换"，必须唯一命中才动手
  • 执行命令——在工作目录跑一条 shell，拿回输出和退出码
  • 找文件 / 搜内容——按通配模式列文件、按正则在内容里搜

同样重要的是这一版故意不做什么。砍掉它们不是偷懒，而是把第一个"能动手"的版本压到小得能一次做对：

  • 不做多轮自动循环（Agent Loop）——只做"单轮"：模型拿到工具结果后再想调工具，本版不让，留给 v0.4
  • 不做规则权限系统——没有 allowlist、不记住选择，只逐次 y/N 问
  • 不做路径沙箱——不限制工具只能碰某个目录，安全全靠"执行前确认"兜底

这份"不做"清单本身就是工程决策。能力每多一分，出错和闯祸的面就大一分——先把边界画死，再谈往里填东西。

SECTION 02

五个新概念，逐个讲透

"工具系统"听着玄，拆开就是五个词。每个先用大白话讲"是什么"，再讲"为什么这么设计"。

工具调用（tool call / function calling）
这是整套系统的地基，也是最反直觉的一点：模型本身碰不到你的电脑。它能做的，只是在回复里"请求"——"我想调用 read_file，参数是这个路径"。真正去读盘、去执行的，是你的程序。程序读完，把结果当成一条新消息发回去，模型才"看见"。 类比：模型是医生，只能开处方（写工具名+参数）；程序是药房，照方抓药。医生永远不碰药柜。这道隔离不是麻烦，是安全的根——再聪明的模型也只能"请求"，落不落地由你这一关说了算。
单轮 vs Agent Loop（多轮自动循环）
本版只做单轮：模型一次回复里发出的并列工具调用（比如同时读两个文件）全部执行、结果一并回灌，模型据此给出最终答案——到此为止。如果它拿到结果后还想再调工具，本版不执行，界面提示"仅支持单轮"。而Agent Loop 是放手让它"调工具→看结果→再调→再看"循环到任务彻底完成。 类比：单轮是"问一句、答一句"；Agent Loop 是"把整件事交给它自己跑完"。先把一来一回做扎实，再谈放它自己跑——循环里每一环都可能翻车，地基不稳就放手，等于放养。
确认门（confirmation gate）
六个工具被劈成两类。只读的（读文件、找文件、搜内容）直接跑，不打扰你。有副作用的（写文件、改文件、执行命令）执行前一律停下来问你 [y/N]，你不点头就不动。 为什么这么劈：看一眼最多浪费几秒；改你的硬盘、跑一条命令，可能不可逆。按"会不会留下痕迹"分流，把打扰精确花在真正危险的动作上。
超时（timeout）
每个工具都在一个有时限的"沙漏"里跑。一条写成死循环的命令，不会把整个助手拖死——到点就放弃那次执行，把"超时了"当成一条错误信息回灌模型，程序继续活着。 类比：就像给每通电话设了上限，对面不挂你也能挂。任何"把控制权交出去"的调用，都要预设一条收回控制权的路。
协议中立（protocol-neutral）
Claude（Anthropic 协议）和国产/OpenAI 系模型，声明工具、回传结果的"电报格式"完全不同。但工具本身不该知道这件事。在文天里，这六个工具一行后端 SDK 都不 import；两家协议的差异，全压在"后端层"那一层消化。 类比：插座国标 vs 英标不一样，但你的电吹风不关心——它只认插头。把"谁都不一样"的脏活关进一间屋子，外面所有人共用一套干净接口。
SECTION 03

真实源码精读

下面四段全是文天真实的源码（删了些枝节，逻辑原样）。每段只看几行，看的是设计长什么样，不是背语法。

① 一个"工具"到底是什么——四样东西加两个开关

整套系统的第一块积木，是一张极简的"工具说明书模板"。任何工具，不管是读文件还是跑命令，都长成同一副样子：

src/wentian/tools/base.py python
class Tool(ABC): name: str # 工具名，模型靠它"点名" description: str # 给模型看的说明书 parameters: dict # 参数的结构（JSON Schema） timeout_s: float = 60.0 # ← 沙漏：最多跑这么久 requires_confirmation: bool = False # ← 危险吗？要不要先问 @abstractmethod def run(self, args: dict) -> str: # 唯一的执行入口 ...

三个属性（名字、说明、参数）+ 一个 run() 入口，是给模型看的"外壳"；两个开关 timeout_s（多久算超时）和 requires_confirmation（要不要先问你）是给执行器看的"安全旋钮"。新增一个工具 = 填一张这样的表，对话流程、界面层一个字都不用改——这就是 F19 说的"统一抽象"。

② 改文件为什么必须"唯一命中"

改文件工具不接受"把所有 foo 换成 bar"这种模糊指令。它要求你给的原文片段，在文件里恰好出现一次。零次或多次，它拒绝动手：

src/wentian/tools/files.py · EditFileTool.run() python
content = path.read_text(encoding="utf-8", errors="replace")count = content.count(old_string)if count != 1: # ← 不是恰好一处，就罢工 raise ToolError( f"Expected exactly 1 occurrence … " f"but found {count}. " # ← 把真实匹配次数告诉模型 "Refine old_string to match exactly one location." )new_content = content.replace(old_string, new_string, 1)

两个设计同时在场。其一，唯一命中才动手：文件里有三处 name = x，模型只想改第二处，"全局替换"会一次改错三个地方——所以零次/多次一律拒绝，宁可不改。其二，也是更妙的：报错时把"实际匹配了几次"也写进去。模型读到"你以为唯一，其实匹配了 3 次"，就能自己把片段写得更精确再试一次。错误信息不是终点，是给模型的修正线索。

③ 工具调用的参数，是一个字一个字"流"过来的

这里藏着流式最反直觉的一处。模型说"我要调 read_file，参数 {"path": "a.py"}"——但这串参数不是一次到齐的，而是像正文一样，被切成碎片陆续推过来：{"pa、th": "a、.py"}……程序得自己按编号把碎片接回去：

src/wentian/providers/openai_compat.py python
for frag in fragments: # 一片片碎片 index = getattr(frag, "index", 0) # 按编号归组 slot = acc.setdefault(index, {"id": None, "name": None, "args": ""}) func = getattr(frag, "function", None) if func is not None: args = getattr(func, "arguments", None) if args: slot["args"] += args # ← 参数碎片，一段段拼起来# 全部到齐后，再尝试解析成参数字典：try: parsed = json.loads(raw_args) if raw_args else {}except (ValueError, TypeError): parsed = None # ← 拼不出合法 JSON，也绝不崩

两个细节值得记住。一是每个字段都用 getattr(..., 默认值) 取——不同厂商的兼容服务器可能少给某个字段，硬取会崩，带默认值就稳。二是参数拼完解析失败时返回 None 而非抛异常：模型偶尔会吐出半截坏 JSON，这时不让它把整条流冲垮，而是标记成"这个调用废了"，往下游交给执行器去优雅地报错。面对不可控的外部输入，先假设它会坏。

④ 执行器：一道闸门，四道检查，永不抛异常

所有工具调用都从同一个入口 execute() 过。它像机场安检，按固定顺序放行；任何一步出问题，都包成一条"结果"交回去，而不是抛出异常把程序炸了：

src/wentian/tools/executor.py · ToolExecutor.execute() python
tool = self._registry.get(name)if tool is None: # 1. 没这工具 return ToolOutcome(…, is_error=True)if arguments is None: # 2. 参数没解析出来 return ToolOutcome(…, is_error=True)if tool.requires_confirmation: # 3. 危险工具：先问你 if not self._confirm(_describe_call(name, arguments)): return ToolOutcome(…, is_error=True, denied=True) # ← 你说不return self._run_with_timeout(…) # 4. 带超时地跑

顺序是有讲究的：先确认工具存在、参数合法，再过确认门，最后才带着超时去跑。无论哪一步出岔子——查无此工具、参数是坏 JSON、你拒绝、跑超时、工具内部崩——返回的都是一条 is_error=True 的 ToolOutcome，异常一个都逃不出这个方法。这样模型总能收到一句人话解释，自己决定改了重试还是向你说明，而程序和会话稳如泰山。这正是 F24"健壮性"的全部含义。

SECTION 04

一次工具调用，从头到尾

把零件拼成整张图。文天的分层延续 v0.1，新长出一整层 tools/。关键约束是这一层纯标准库——零后端 SDK、零界面库，所以它能被离线测试、也能被任何协议复用：

cli.py — 装配车间把六个工具登记进 registry，配好 executor（确认门跟随是不是真终端）
↓注入
repl.py — 对话主持人把工具声明随请求发出；流结束后若有工具调用，进入"单轮工具回合"
↓每次调用经 ↓ 执行、交 ↘ 显示
tools/
执行层registry 登记 · executor 闸门 · 六个工具
纯标准库
providers/
翻译官声明工具、拼接流式碎片、回传结果——两家协议的差异全在这层
↓对话与工具结果一起存档
session.py — 记录员工具调用与结果作为历史持久化，--continue 能接着引用

而一次工具往返，在这张图里是这样走完七步的（每步标了它住在哪个文件）：

1
带着"工具清单"提问repl.py

每轮请求都附上 registry.specs()——一份协议中立的工具声明。后端层再把它翻译成各家要的电报格式发出去。

2
模型回复里夹着"工单"providers/

流式回复中，正文、思考之外可能夹着工具调用。后端层把分片到达的参数碎片按编号拼回完整的 ToolCallEvent。

3
先把工单收齐，流结束再动手render.py

渲染层一边显示正文，一边把工具调用静静收集。等这一轮流彻底结束，主持人才统一处理——不打断正文呈现。

4
逐个执行：显示→过闸门→显示结果executor.py

每个调用先打印 ⏺ 工具名(参数)，再过执行器（确认门+超时），最后打印 ⎿ 成功/失败/已拒绝。结果作为一条 tool 消息进历史。

5
先落盘，再继续session.py

工具可能真改了硬盘。所以在发第二轮请求之前先存档——万一下一步崩了，已经发生的副作用也不会从历史里丢失。

6
带着工具结果，再问一次repl.py

把工具结果回灌，发起第二轮。模型读到结果，给出最终的、有据可依的回答。这一轮的正文照常进历史。

7
到此为止：单轮的闸刀repl.py

如果第二轮里模型又想调工具——不执行，提示"仅支持单轮"。且这些没被执行的工具请求绝不存进历史（一个"没有答案的工具调用"会让下次请求直接报错）。已生成的文字照常保留，本轮收工。

SECTION 05

六条能带走的心法

下面六条，跟"终端 AI 助手"没有绑定关系。它们是同一批工程思想在这个项目里的化身——以后你写任何让程序"代替人去动真实世界"的系统，都还用得上。每条配一句触发口令：哪天你写代码时心里冒出那句话，这条心法就启动了。

模型只能派工单，不能动手

任何让 LLM 接触真实系统（文件、命令、数据库、对外请求）的设计，中间都必须夹一道"程序真正执行"的关。模型再聪明，也只能请求；落不落地，由你这一层决定。能力边界，就是安全边界。

同一个它出现在 →function calling浏览器沙箱数据库存储过程操作系统系统调用
危险的事，执行前必须有人点头

把动作按"会不会留下不可逆痕迹"分流：只读的直接放行，有副作用的执行前停下来确认。这一刀，是一切 agent 安全的第一刀——区分"看"与"改"，再决定哪些需要人在回路里。

同一个它出现在 →sudo 密码转账短信验证码数据库迁移确认删库前的二次弹窗
非交互环境，默认拒绝

文天判断："没有真终端（管道、CI、自动化）时，没人能按 y，那就让确认门一律返回否"——副作用工具自动不执行。出问题时偏向安全的那一侧（fail-safe），而不是偏向放行（fail-open）。默认值，是最沉默也最重要的设计。

同一个它出现在 →防火墙默认拒绝最小权限原则保险丝门禁断电即锁
错误不抛出，包成结果回灌

工具失败——文件不存在、命令出错、超时、参数是坏 JSON——都不该把程序炸掉，而是把"为什么失败 + 实际情况（匹配了几次、超时多久）"喂回给模型，让它自己改了重试或向你解释。错误信息是给对方的修正线索，不是终点。

同一个它出现在 →HTTP 4xx 带 body编译器报错带行号表单校验提示异常重试退避
协议差异，只压在一层

"谁都不一样"的脏活——Anthropic 和 OpenAI 各自的工具声明格式、流式解析、结果回传——全部关进后端层那一间屋子。工具层对协议一无所知，一行 SDK 都不 import。换后端、加后端，工具一个字不用动，还能离线测试。

同一个它出现在 →驱动 / HAL 硬件抽象层ORMUSB 协议适配器模式
先把副作用落盘，再做下一步

工具真的改了硬盘之后，文天先存档，再发第二轮请求。万一下一步崩了，已经发生的事实也不会从历史里蒸发。凡是"不可逆操作 + 后面还有可能失败的步骤"，就先把已发生的记牢，再往前走。

SECTION 06

测一测：考的是取舍

八道题，全考"为什么这么设计"，不考路径、字段名、常量数字。先自己想清楚，再点开看参考答案——道理对就给分，术语不精确不扣分。给自己一个等第：甲（讲透取舍）/ 乙（抓住要点）/ 丙（方向对但说不全）/ 丁（再读一遍上面）。

Q1为什么不让模型直接读写文件，非要它"请求"程序代劳，多绕一道？
要点：因为能力边界就是安全边界。模型只能"请求"、不能"落地"，意味着无论它被诱导成什么样，真正动硬盘的永远是你可控的那一层程序——可以在中间加确认、加超时、加日志、加拒绝。把执行权攥在自己手里，模型再聪明也越不过这道关。这就是 function calling 的本质：不是给模型手，是给它一张能被你审核的工单。
Q2读文件不问、写文件要问 y/N——这条线为什么这么画？
要点：按动作的可逆性 / 代价分流。只读最多浪费几秒、不留痕迹；写、改、执行命令可能造成不可逆的后果。把"打扰用户"这件成本不低的事，精确花在真正危险的动作上——既不让危险动作偷偷发生，也不让无害动作把你烦死。
Q3把 wentian 用管道跑（没有真终端），它收到一个写文件请求会怎样？为什么这样设计？
要点：自动拒绝。没有真终端时没人能按 y，确认门就恒返回否，副作用工具一律不执行。这是 fail-safe（偏向安全）的默认值：拿不准的时候，宁可不做，也不要在无人看管的环境里悄悄改了你的文件。对照防火墙"默认拒绝"、最小权限——安全系统的默认值都该倒向"不放行"。
Q4改文件要求原文"恰好出现一次"。多处匹配时，为什么还要把"实际匹配了几次"也告诉模型？
要点：为了让模型自我修正。只说"失败了"，模型无从下手；告诉它"你以为唯一，其实匹配了 3 次"，它就知道该把原文片段写得更长更精确，再试一次。错误信息带上"现场实况"，就把一次失败变成一条可操作的修正线索——反馈闭环，而不是死胡同。
Q5模型调了一条会死循环的命令，为什么不会把整个助手卡死？
要点：因为每次执行都套着超时。到点还没跑完，就放弃那次执行、把"超时"当错误回灌，程序收回控制权继续活着。凡是"把控制权交给一段你不完全可控的代码"，都要预设一条到点收回控制权的退路——否则一次卡死就能拖垮全局。
Q6工具执行出错时，为什么不让异常自然抛出去，而要包成一条 is_error 的结果？
要点：异常抛出去会炸掉程序、中断会话；包成结果，则模型能"读到"失败原因，自己决定改了重试还是向你说明，而 REPL 稳稳活着等下一句。把"失败"从"崩溃"降级成"一条普通的消息"，整个系统的健壮性就上了一个台阶——失败是常态，要被当数据处理，不是被当事故。
Q7本版"单轮"：模型拿到工具结果后又想调工具，被拒。为什么这些没被执行的工具请求绝不能存进会话历史？
要点（略深）：因为一条"工具调用"在协议里必须配一条"工具结果"才算完整。如果把没执行的工具请求存进历史，下次发请求时，历史里就躺着一个没有答案的工具调用——后端会因此直接报错（400），把整个会话弄脏。所以宁可只存正文、丢掉这些悬空的请求，也要保证历史永远是"自洽"的。这是"持久化状态必须时刻合法"的纪律。
Q8工具层为什么一行后端 SDK 都不 import？这换来什么？
要点：换来三件事：① 换后端、加后端时工具一个字不用改（协议差异全在后端层）；② 工具能在完全不联网、不装任何厂商 SDK 的情况下被自动化测试；③ 同一套工具被两家协议共用，不重复造。把"谁都不一样"的脏活隔离在一层里，外面所有人共享一套干净接口——这是分层解耦最直接的回报。

八题里若有四题以上够到"乙"，说明你已经拿到了这一版真正想给你的东西——不是六个工具怎么写，而是"让程序代替人去动真实世界"时，那几道必须设的关。

SECTION 07

自己跑起来

好消息：v0.3 没有任何新配置。v0.1 那份 ~/.config/wentian/config.yaml 原样能用——启动后，模型自动获得这六个工具。三步体验：

1
在你的项目目录里启动

uv run wentian。工具的"工作目录"就是你启动时所在的目录——它能看到、动到的，是这里的文件。

2
让它"看"——只读工具直接跑

问一句 读一下 README，讲讲这个项目是干嘛的。你会看到 ⏺ read_file 一闪而过，然后是基于真实内容的回答。找文件、搜代码同理，不打扰你。

3
让它"动"——副作用工具会先问你

试 新建一个 hello.txt，写句你好。这次会弹出 执行该操作？[y/N]——看清楚它要做什么，再决定点不点头。拒绝了，文件系统一动不动，模型会在回答里说"被你拒绝了"。

想确认工具是真在干活、不是模型嘴上说说？让它做一件它编不出来的事：用 run_command 跑一下 `date`，告诉我现在几点。模型没有时钟，只有真执行了命令、拿到回灌的输出，才能答对当前时间。答对了，整条链路就实锤了。

最后，把这一版压成三句话

  • 给能力，先给边界——模型只能"请求"，落地永远经过你可控的一层；能力边界就是安全边界。
  • 危险的动作，默认从严——副作用先确认，没人看管时默认拒绝。安全系统的默认值，要倒向"不放行"。
  • 失败当数据，不当事故——工具出错就包成一条消息回灌，让模型自愈，让程序续命。

这三条和"工具系统"也没绑定。下次你给任何程序接上"能动真实世界"的能力——哪怕不是 AI——它们照样成立。下一站 v0.4：把"单轮"拆掉，让它自己跑完一整件事（Agent Loop）。
