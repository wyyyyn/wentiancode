让 AI 助手自己跑完
一整件事

这是 WentianCode（文天）v0.4 的搭建记录。上一版它长出了手，能读写文件、跑命令——但只能"动一下，停一下"，每一步都得你催。这一版给它装上 Agent Loop：想 → 调工具 → 看结果 → 再想，自己循环到任务完成。还是不需要编程背景，但每个取舍都讲透——为什么"放手"之前必须先装刹车、为什么大脑和界面要彻底分家、为什么有些工具能一起跑、有些必须排队。

SECTION 01

从"一步一停"到"自己跑完"

上一版的文天会动手了——可它一次只动一下。你说"读一下这个文件"，它读；可它读完之后想"我得再改一处"，对不起，本版不让，到此为止，得你再说一句它才能继续。每一步都要你在旁边盯着、催着。它像一个能干但没主动性的实习生：交代一句做一句，不交代就停。

v0.4 干的事，是让它自己把一整件事跑完。从这一版起，你给一个多步任务——"找到那个文件、改一处、再跑测试确认"——它会自己想第一步该干嘛、调工具、看结果、决定下一步、再调……一轮接一轮，直到任务真正完成，中途不用你催。这就是 Agent Loop。

wentian — 一次自主的多轮循环
$ wentian 文天> 找到定义 status_line 的文件，把那一行的中文标点改成英文，再跑测试确认没破坏 ⏺ search_text(pattern='def status_line') # ← 第 1 轮：先找 ⎿ 成功 · src/wentian/repl.py:380 ⏺ read_file(path='src/wentian/repl.py', offset=380) # ← 第 2 轮：再读 ⎿ 成功 · def status_line(self) -> str: … ⏺ edit_file(path='src/wentian/repl.py', …) # ← 第 3 轮：动手改 执行该操作？[y/N] y # ← 副作用，先问你 ⎿ 成功 · Edited repl.py: replaced 1 occurrence. ⏺ run_command(command='uv run pytest -q') # ← 第 4 轮：自己验证 执行该操作？[y/N] y ⎿ 成功 · 504 passed 改好了，测试全绿。改动落在 status_line 那一行…… # ← 第 5 轮：收束总结 tokens 输入 3284 · 输出 591 · 共 5 轮

同一个任务，v0.3 要你催四次，v0.4 一句话跑完五轮。但"放手让它自己跑"是把双刃剑——跑飞了怎么办？所以这一版的重点，根本不是"循环"两个字，而是怎么让循环安全地停下来。这一版要立住的五件事：

  • ReAct 多轮循环——想→调工具→看结果→再想，直到不再需要工具
  • 五个停机条件——尤其一个轮数上限，跑飞了也能兜住
  • 异步事件流——把"循环大脑"和"屏幕界面"彻底分家
  • 安全分批——能并发的只读工具一起跑，危险的串行排队
  • 计划模式——/plan 只许看、先出计划，/do 再放手干

和上一版一样，故意不做的事同样是设计：

  • 不做规则权限系统——没有"总是允许"、不按目录授权，副作用仍逐次 y/N 问
  • 不做上下文压缩——长任务撑爆上下文窗口的处理，留给后续版本
  • 不做工具执行期间的中断——只能在模型"说话"时按 Esc，长命令靠超时兜底

给自主权这件事，能力越大，跑飞的后果越重。所以这一章一半的篇幅，其实都在讲"怎么停"——五个停机条件，是这版真正的主角。

SECTION 02

六个新概念，逐个讲透

"Agent Loop"听着高级，拆开是六个词。每个先用大白话讲"是什么"，再讲"为什么这么设计"。

ReAct 循环（想—做—看，再来一遍）
这是整章的地基。ReAct = Reason（想）+ Act（做）+ 看结果，循环往复。模型先想"这一步该干嘛"，发出工具调用（做），程序执行后把结果塞回去（看），模型据此想下一步……直到它觉得"任务完成了，不需要再调工具"，循环才停。v0.3 是这个循环被掐死在第一圈，v0.4 是放开让它自己转。 类比：像人修东西——看一眼（哪坏了）、拧一下（动手）、再看一眼（好没好）、不行再拧。不是一口气想完所有步骤，而是走一步看一步、边做边调。这种"做了再看、看了再调"的节奏，正是 agent 比一次性问答强的地方。
停机条件（循环的五种"刹车"）
放手让它自己转，最怕转不停。所以文天给循环装了五个刹车，任一触发就收场：① 模型说"完事了"（不再要工具）；② 撞上轮数上限（默认 20 轮，兜底防失控）；③ 你按 Esc 中断；④ 模型连着两轮净调"根本不存在的工具"（防它钻牛角尖空转）；⑤ 流式请求出错。 为什么轮数上限最关键：前四个都依赖"某件事正常发生"，唯独它不依赖任何前提——哪怕模型彻底跑飞、陷进死循环，数到 20 也必停。它是兜底的那一道，是"万一其它都失灵"时最后拦住你的墙。
异步事件流（大脑和界面分家）
循环里发生的一切——这轮开始了、吐了段正文、调了个工具、拿到结果、用了多少 token、循环结束了——都被打包成一个个"事件"，顺着一条流往外发。"循环大脑"只管产生事件，"屏幕界面"只管消费事件去画，两边互不知道对方怎么实现。 类比：像电视台和电视机——台里只管把信号播出去，不关心你家是液晶还是投影；你换电视，台里一个字不用改。把"算什么"和"显示什么"拆开，将来想换个网页界面、或拿"事件记录器"把整场循环录下来做测试，循环逻辑一行都不用动。
双路收集（边显示，边攒账）
模型吐正文时，文天同时走两条路：一条把每个字立刻推给屏幕（你看到逐字流式，观感和以前一样），另一条悄悄把这一整轮的完整内容攒起来——全部文字、所有工具调用、用量——留给循环大脑做决策、写进历史。显示不等攒完，攒账不漏一个字。 类比：像直播现场——画面实时播给观众（显示），同时录像机完整录下来存档（攒账）。实时的那一份图快，完整的那一份图准，两个需求别互相将就，各走各的路。
安全分批（能一起的一起，危险的排队）
模型一轮可能同时要调好几个工具。文天按安全性分批：连续的只读工具（读文件、搜内容）并发一起跑，谁先回来不管、最后按原顺序对齐；有副作用的（写、改、跑命令）一个一个串行，且不许越过它前后的只读操作。 为什么这么分：同时读三个文件，互不干扰，一起读省时间；但"读 A、写 B、读 C"里，C 必须等 B 写完——否则可能读到写之前的旧内容。只读之间无所谓顺序，一碰到"改"，顺序就是对错。按"会不会互相影响"决定谁能并行。
计划模式（先勘察，再动手）
两段式工作流。敲 /plan，文天只把只读工具给模型，并叮嘱它："先勘察、出一份分步计划，别改任何东西。"你看完计划满意了，敲 /do 切回全套工具放手执行。模型在计划模式里硬要写文件？被一道拦截挡下，告诉它"现在只能看"。 类比：像装修——先量房出方案（plan），你点头了，工人才进场砸墙（do）。把"想清楚"和"动真格"分成两段，在改坏任何东西之前，先有一个你能审、能改、能喊停的关口。
SECTION 03

真实源码精读

下面五段全是文天 v0.4 真实的源码（删了枝节，逻辑原样）。每段只看几行，看的是设计长什么样，不是背语法。

① 循环的骨架：一个带刹车的 for 循环

整章的心脏，是 AgentLoop.run() 里这个循环。它读起来出奇地朴素——一个从 1 数到上限的 for，每轮跑一遍"流→决策"，几个 return 就是几种刹车：

src/wentian/agent/loop.py · AgentLoop.run() python
for n in range(1, self._max_rounds + 1): # ← 轮数上限：兜底刹车 yield RoundStart(n) # 流阶段：桥 + 双路收集器消费这一轮模型回复 … round_result = collector.result(interrupted=interrupted) if not round_result.tool_calls: # ← 不再要工具：正常收束 messages.append({"role": "assistant", "content": text}) yield AgentDone(StopReason.COMPLETED, …); return if n == self._max_rounds: # ← 到顶还想调：刹停，不再执行 messages.append({"role": "assistant", "content": text}) yield AgentDone(StopReason.MAX_ROUNDS, …); return # 否则：分批执行工具 → 原子入史 → 进入下一轮

两处刹车都值得记。"不再要工具"就是正常完成——循环的终点不是某个计数，而是模型自己说"够了"。而 n == max_rounds 这一刀更微妙：撞上限时故意不执行最后那批工具，只存已生成的文字。为什么不"再跑最后一批"？因为上限是失控保护——刹车点上还放行一批，等于刹车失灵。这就是 F29 五停机条件里最该咂摸的那一个。

② 红线：工具调用与结果，必须"成块"一起写进历史

这是整版最硬的一条不变量。一条带工具调用的 assistant 消息，和它对应的工具结果，必须作为一个整体写进历史——绝不允许写了一半。代码用"先全收齐、再一次性追加"来保证：

src/wentian/agent/loop.py · 工具阶段尾声 python
# 全部工具结果收齐后，才开始往历史里写：assistant_msg = { "role": "assistant", "content": round_result.text, "tool_calls": [{"id": c.id, "name": c.name, "arguments": c.arguments if c.arguments is not None else {}} # ← 坏参数入史存 {} for c in round_result.tool_calls],}messages.append(assistant_msg)for call, outcome in results: # ← 紧跟着，逐条工具结果 messages.append({"role": "tool", "tool_call_id": call.id, …})yield RoundEnd(n, tool_results=len(results)) # 写完整，才发 RoundEnd（落盘点）

为什么是红线？因为在两家协议里，一个"工具调用"必须配一个"工具结果"才算合法。如果历史里躺着一个有调用、没结果的 assistant 消息，下次请求会被后端直接 400 拒收，整个会话就废了。所以代码等所有结果都拿到手，才一次性把 assistant + 全部 tool 消息追加进去——要么这一整块都在，要么都不在。哪怕中途按 Ctrl+C，历史也永远是"成对自洽"的。这是"持久状态任何时刻都得合法"的纪律。

③ 安全分批：只读的一起跑，但结果按原序对齐

一批只读工具怎么"一起跑又不乱序"？诀窍是先把所有任务都发出去（真并行），再按原始顺序一个个收结果：

src/wentian/agent/batch.py · run_wave() python
if wave.concurrent: # 只读段：一起跑 tasks = [asyncio.ensure_future(run_call(c)) for c in wave.calls] # ← 先全部起跑 for call, task in zip(wave.calls, tasks): yield ("started", call, None) outcome = await task # ← 但按原顺序收结果 yield ("result", call, outcome)else: # 副作用/未知：一个一个来 for call in wave.calls: yield ("started", call, None) outcome = await run_call(call) # 串行：跑完一个才下一个

关键在"先起跑、后按序收"的拆分。ensure_future 把三个只读调用同时丢出去，它们的墙上时间是"最慢那个"而不是"三个相加"；但收结果时按 wave.calls 的原始顺序 await，所以哪怕第三个先跑完，也得排队等前两个——回灌进历史的顺序永远和模型给的顺序一致。一边要并发的快，一边要顺序的稳，这段代码把两者同时拿下。并发是为了省时间，定序是为了可复现。

④ 同步流接进异步循环：为什么坚持用守护线程

这里有个反直觉的工程决定。模型的流是同步的（一个普通的 Python 生成器），可循环是 异步的。怎么把同步的流喂进异步的世界？文天用一根守护线程当桥，而刻意不用看起来更省事的 asyncio.to_thread：

src/wentian/agent/bridge.py · StreamBridge python
class StreamBridge: # 同步流 → 异步世界的桥 def __init__(self, events): self._queue = queue.Queue() # 线程安全的传送带 self._thread = threading.Thread(target=self._run, daemon=True) # ← 守护线程 self._thread.start() async def drain(self, interrupt): while True: try: kind, payload = self._queue.get_nowait() # 非阻塞取 except queue.Empty: await asyncio.sleep(0.05); continue # ← 轮询，绝不阻塞事件循环

为什么不用现成的 asyncio.to_thread？因为 asyncio.run() 收尾时会等它的默认线程池干净退出——万一有个工具的确认 input() 正卡在那等你按回车，Ctrl+C 之后整个程序会冻死，直到你回去敲一下回车。而专用守护线程不一样：进程要退就退，它挂着也不拦着。事件循环这头只做"取一下、没有就睡 50 毫秒"的非阻塞轮询，永远不会被拖住。这是踩过的坑——别让收尾流程去 join 一个可能永远不回来的阻塞调用。

⑤ 计划模式的"第二道保险"：名单外的工具，根本不交给执行器

计划模式已经只把只读工具的"说明书"给模型了——但模型还是可能硬报一个写文件的调用。光靠"不给说明书"不够，循环里还有第二道闸：

src/wentian/agent/loop.py · 工具阶段 run_call() python
async def run_call(call): # 计划模式：名单外的工具，绝不交给 executor 真执行 if classify(call, self._registry, self._allowed_tools) == "blocked": return self._make_blocked_outcome(call) # ← 合成一条"被拦截"结果回灌 return await call_in_thread( self._executor.execute, call.id, call.name, call.arguments)

这是"双保险"：第一道是"不给说明书"（声明过滤，挡住一般的引导），第二道是这里——名单外的调用根本不进执行器，而是当场合成一条"计划模式下不可用"的结果回灌给模型。注意它合成的是一条普通的错误结果，不是抛异常、也不算"用户拒绝"——模型读到这句话，就明白"哦现在只能看"，自己改口。一道防线挡君子，两道防线挡"硬闯"。越是依赖外部（模型）守规矩的地方，越要在自己这头再兜一层。

SECTION 04

一次自主循环，从头到尾

把零件拼成整张图。v0.4 在 v0.3 之上新长出一整层 agent/——它是异步的循环大脑。关键是这层夹在中间：下面的工具/后端仍是同步的，上面的界面也是同步的，它用线程桥把两头接起来，自己跑 asyncio：

repl.py — 对话主持人每轮用 asyncio.run() 驱动一次循环；把事件映射成屏幕动作；管落盘与回滚
↓asyncio.run 驱动，事件流回传
agent/ — 循环大脑（异步）loop 调度 · bridge 桥接同步流 · collector 双路 · batch 分批
只认契约，不认协议
↓每轮：发请求 ↓ 执行工具 ↘ 攒结果
providers/
翻译官同步流式生成器；两家协议的差异在此消化
tools/
执行层registry · executor 闸门 · 六个工具
纯标准库
↓每轮工具结果即时存档
session.py — 记录员每轮原子入史后逐轮落盘，--continue 能接着引用（沿用 v0.3）

而一次多轮循环，在这张图里是这样转完的（每步标了它住在哪个文件）：

1
带着问题进循环repl.py

主持人把这一回合交给 asyncio.run()，启动 AgentLoop。从这里起，控制权进了异步世界，主持人只等着接事件、画屏幕。

2
守护线程把同步流喂进来bridge.py

模型的流是同步的。一根守护线程在后台把它"翻译"成异步循环能 await 的事件——还顺带盯着 Esc，你想中断时 50 毫秒内就能收手。

3
双路：边显示边攒账collector.py

每段正文一边立刻发给屏幕（你看到流式），一边攒进这一轮的完整记录——文字、工具调用、用量，全留着给下一步决策用。

4
决策：停，还是继续？loop.py

这一轮流结束，大脑做判断：模型不要工具了？正常收场。撞上轮数上限了？刹停。都不是——那就进工具阶段。五个停机条件就在这里把关。

5
安全分批，执行工具batch.py

把这轮的工具调用按安全性切成几"波"：连续只读的并发跑，副作用的串行跑（确认门、超时照旧）。每个调用先显示 ⏺，结果回来再显示 ⎿。

6
原子入史，逐轮落盘loop.py → session.py

全部结果收齐，把 assistant + 所有工具结果成块追加进历史，再发 RoundEnd。主持人收到就落盘——副作用已经真发生，崩了也不能丢。

7
回到第 2 步，再转一圈loop.py

带着刚拿到的工具结果，发起下一轮请求。模型读到结果、想下一步……如此循环，直到第 4 步某个停机条件触发。

8
收场：五种原因之一loop.py → repl.py

循环以一个 AgentDone 结束，带着停机原因。主持人按原因打印提示（撞上限/未知工具空转给黄字提醒），再把这一回合的总 token 用量显示出来。

SECTION 05

六条能带走的心法

下面六条，跟"终端 AI 助手"没有绑定。它们是同一批工程思想在这个项目里的化身——以后你写任何"放手让程序自己跑一连串动作"的系统，都还用得上。每条配一句触发口令：哪天你写代码时心里冒出那句话，这条心法就启动了。

放手之前，先装刹车

任何"让它自己循环/重试/递归直到完成"的设计，都必须有一个不依赖任何前提的兜底上限。别指望"它自然会停"——正常逻辑都可能失灵，唯独一个硬性的次数/时间上限不会。给自主权的同时，先把那道最后的墙砌好。

算逻辑的，别让它管画屏幕

SECTION 06

测一测：考的是取舍

八道题，全考"为什么这么设计"，不考路径、字段名、常量数字。先自己想清楚，再点开看参考答案——道理对就给分，术语不精确不扣分。给自己一个等第：甲（讲透取舍）/ 乙（抓住要点）/ 丙（方向对但说不全）/ 丁（再读一遍上面）。

Q1自主循环为什么一定要设一个轮数上限？模型不是"觉得做完了自然会停"吗？
要点：因为"自然会停"依赖模型行为正常，而这恰恰不能假设。模型可能陷进死循环（反复调同一个工具不收敛）、可能被绕进牛角尖、可能因为某种误判永远觉得"还差一步"。轮数上限是唯一不依赖任何前提的刹车：哪怕其它判断全失灵，数到 20 也必停。这就是兜底安全网的意义——它存在不是为了"正常情况"，是为了"万一"。
Q2撞上轮数上限时，模型还想调工具。为什么不"好心"再帮它跑完最后这一批，而是直接刹停？
要点：因为上限是失控保护，刹车点上再放行一批，等于刹车失灵。如果"到顶了还能再执行一批"，那这"一批"里又可能要求新工具，逻辑上你永远能找到理由再放一次——上限就名存实亡了。所以到点就是到点：只保留已生成的文字，不再执行任何工具。把刹车做成真的刹得住，比"再通融一次"重要得多。
Q3为什么要让"循环大脑"和"屏幕界面"彻底分开，中间隔一条事件流？合在一起写不是更省事？
要点：为了各自能独立替换和验证。大脑只管发事件、不碰屏幕，界面只管消费事件、不懂循环——于是你可以：换个网页界面而循环一行不改；用一个"事件记录器"代替真界面，把整场循环录下来逐条断言（这正是它能被离线测试的原因）；将来加个日志层也只是多一个消费者。合在一起写当下省事，但任何一边想动，都得牵扯另一边。解耦的回报是延迟兑现的，但很大。
Q4一轮里模型要"读 A、写 B、读 C"。为什么不能把两个读操作都并发了，图个快？
要点：因为 C 在 B 之后，可能依赖 B 的写入。如果把 A、C 两个读一起并发，C 就可能在 B 写完之前读到旧内容——结果错了。只读之间没有先后无所谓，可一旦中间夹着"改"，顺序就是对错。所以分批的规则是：连续的只读才合并并发，碰到副作用就断开、串行、保持原位。能并发的前提是"互不影响"，不是"看起来都能跑"。
Q5带工具调用的 assistant 消息和它的工具结果，为什么必须"成块"一起写进历史，不能先写一半？
要点（略深）：因为在协议里，一个"工具调用"必须配一个"工具结果"才算合法成对。如果先写了 assistant（带调用）、结果还没写就崩了/被打断，历史里就留下一个有调用没结果的残缺消息——下次发请求时后端直接 400 拒收，整个会话报废。所以代码等所有结果都收齐，才一次性把 assistant + 全部工具结果追加进去：要么整块都在，要么都不在。持久状态任何时刻都必须是自洽的，这跟数据库事务"要么全成、要么全不"是同一条纪律。
Q6把同步的流接进异步循环，为什么坚持用守护线程，而不用现成的 asyncio.to_thread？
要点（略深）：因为 asyncio.run() 收尾时会等它的默认线程池干净退出。万一某个工具的确认 input() 正卡在线程池里等你按回车，Ctrl+C 之后整个程序会冻死，直到你回去敲一下回车——这是很糟的体验。专用守护线程没这问题：进程要退就退，它挂着也不拦着；事件循环这头只做非阻塞轮询，永不被拖住。这是个具体的坑：别让"收尾流程"去等一个可能永远不返回的阻塞调用。方便的抽象不一定适配你的退出时序。
Q7计划模式已经只把只读工具的"说明书"给模型了，为什么循环里还要再加一道"拦截"？这不是重复吗？
要点：不是重复，是双保险，因为两道防的是不同情况。"不给说明书"（声明过滤）挡的是引导——模型一般不会去调一个没声明的工具。但模型仍然可能硬报一个写文件的调用（它脑子里"记得"有这个工具）。这时第二道闸生效：名单外的调用根本不进执行器，当场合成一条"计划模式下不可用"的结果回灌。一道防君子，两道防硬闯。凡是安全依赖"外部（模型）守规矩"的地方，都要在自己这头再兜一层，因为你控制不了对方。
Q8循环中途某一轮流式出错了。为什么是"丢掉这一整轮"，而不是"保留已经吐出来的半截文字"？
要点：因为半截文字进不了一个合法的历史。出错那轮可能正吐到一半工具调用、或正要配工具结果，此时强行保留半截，很容易留下前面说的"有调用没结果"的残缺状态，污染历史。而之前已经完整跑完的每一轮，早就成块落进 messages 了——丢掉出错的当前轮，不影响它们。所以策略是：当前轮整个丢弃、屏幕上报个错、会话继续可用。宁可少存这半轮，也要保证历史永远干净。残缺的数据比缺失的数据更危险。

八题里若有四题以上够到"乙"，说明你已经拿到了这一版真正想给你的东西——不是 Agent Loop 怎么写，而是"放手让程序自主跑一连串动作"时，那几道必须设的关：刹车、解耦、原子、定序、桥接、两段式。

SECTION 07

自己跑起来

好消息：v0.4 没有任何新配置。v0.1 那份 ~/.config/wentian/config.yaml 原样能用。和 v0.3 不同的是——这次你给它一个多步任务，然后放手。三步体验：

1
给一个需要好几步的任务

uv run wentian 启动后，试 找出当前目录最大的 .py 文件，数一下它有多少行。你会看到它自己 find_files → run_command 一轮接一轮，不用你催。

2
用计划模式先勘察、再动手

敲 /plan 把 README 的安装说明改成 uv 方式。它只会读、搜、给你一份计划——不碰任何文件。看顺眼了，敲 /do 按计划执行，它才真正动手（写文件时照样问你 y/N）。

3
看一眼"刹车"

循环每跑完一轮都在攒；正常任务几轮就收。回合结束那行 tokens … · 共 N 轮 就是它这次想了几步。哪天它真跑飞了，撞上 20 轮上限会自己停下并提示你——刹车一直在那。

想确认它是真在"自主多轮"、不是一次答完？给它一个必须靠前一步结果才能做下一步的任务：找到行数最多的那个测试文件，把它的行数告诉我。模型没法凭空知道哪个文件最长——它必须先 find、再逐个 run_command 数行、比较，最后才能答。看着它一轮轮逼近答案，自主循环就实锤了。

最后，把这一版压成三句话

  • 给自主，先给刹车——任何"让它自己跑到完"的循环，都要有一道不依赖前提的兜底上限。
  • 大脑与界面分家——算逻辑的只发事件，画屏幕的只消费事件；解耦换来的是哪一处都能独立替换、独立验证。
  • 持久状态永远自洽——配套的数据要么整块落、要么都别落；任何时刻去看历史，它都得是合法的。

这三条和"Agent Loop"也没绑定。下次你给任何系统接上"自主跑一连串动作"的能力——爬虫、流水线、自动化运维——它们照样成立。到这里，文天从"会聊天"（v0.1/v0.2）、"能动手"（v0.3）走到了"自己干活"（v0.4）。一个真正能用的 coding agent，地基齐了。
